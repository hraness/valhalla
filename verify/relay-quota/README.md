# Relay item and quota publication

This finite safety model checks the shipping TLS relay's joint item/charge
publication, exact duplicate position and charge ownership, stable credential
identity through token replacement, and retention before receipt release.
These cumulative storage quotas are independent of the sender's retry budget
and the service's transient request/connection work windows.

## Production correspondence

| Model boundary | Shipping boundary | Exercised correspondence |
| --- | --- | --- |
| `StageCharge`, `StageItem`, `Commit` | `tls::service::put` writes `tls_charges` and calls `FileStore::put_staged` inside one immediate SQLite transaction | `publication_failure_rolls_back_quota_and_poisoned_service_requires_reopen` injects an actual item insert failure after charge staging and checks that neither item nor charge survives. |
| Duplicate admission, `RetryKeepsPositionAndCharge` | `put` skips a charge already bound to the digest; `put_staged` returns the existing mailbox position | `lost_receipt_reopen_retries_exact_ciphertext_at_original_position` and the compound sender/TLS trace verify the original exact item and position after a lost response. |
| `RotateToken`, `StableIdentitySpend` | `Service::new` preserves immutable `tls_keys` quotas and existing `tls_charges` under a stable credential ID | `permissions_wrong_token_and_rotation_preserve_durable_quota` and the compound trace replace tokens without renewing quota. |
| `Barrier`, `ReceiptAfterDurableRetention` | `put` commits, calls `store.sync`, then constructs the successful receipt | The compound trace intentionally loses a completion only after a real successful PUT and confirms retained item/charge readback before restarting the service. |
| `Reopen` | `FileStore::open` plus `Service::new` verify the retained mailbox and charge ledger before serving | Existing tests reject uncharged compatibility writes, corrupt charge ownership and changed immutable quotas. |

The production files are `crates/vhalla-private-native/src/relay/mod.rs` and
`relay/tls/service.rs`. Tests live in `relay/tls/tests.rs`.
`formal_relay_lost_receipt_resume_preserves_custody_and_quota` also drives
production `DeliveryStore`: lose successful completion, reopen, replace token
under the same ID, exhaust two denied attempts, explicitly resume, receive the
original position, and refuse a new item against the original quota. One bound
listener is retained across service restarts so address/name/CA/namespace stay
unchanged. The final readback checks exact ciphertext and one original-owner
charge for exactly the payload length.

## Cases and counterexamples

| Configuration | Required result |
| --- | --- |
| `normal.cfg` | All invariants pass with one item and three abstract payload-byte units per key. |
| `byte-quota.cfg` | All invariants pass with two items allowed but only two payload-byte units per key; the two differently sized items cannot both fit under one key. |
| `mutant-early-charge.cfg` | `ItemsChargedTogether` fails when a charge becomes durable before its item transaction. |
| `mutant-duplicate-charge.cfg` | `RetryKeepsPositionAndCharge` fails when an exact duplicate receives another charge. |
| `mutant-duplicate-position.cfg` | `RetryKeepsPositionAndCharge` fails when a duplicate moves to a fresh mailbox position while its single original charge is unchanged. |
| `mutant-token-reset.cfg` | `StableIdentitySpend` fails when token replacement forgets the stable identity's accumulated charges. |
| `mutant-early-receipt.cfg` | `ReceiptAfterDurableRetention` fails when a receipt is constructed before the item has passed the durability barrier. |

`original` and `owner` record the first committed position and charge owner;
they are history instrumentation, never admission inputs. Receipt records
preserve the position and durability observation at release, so a later retry
cannot repair a historically incorrect receipt. No production defect was
established in this slice; these are deliberate failing mutations.

## Bounds and assumptions

- Two exact item identities with payload sizes one and two abstract byte units,
  two stable credential IDs, four admitted PUTs, one owner-token replacement
  and two process interruptions. The other credential supplies independent
  authenticated work permission; duplicates retain their original owner.
- Transactions serialize under the service mutex. A completed SQLite commit
  survives a process interruption; uncommitted staged writes disappear. A
  separate successful barrier precedes receipt construction. Physical power
  loss, SQLite/fsync correctness and concurrent storage writers are not proved.
- Reopen abstracts successful validation and its new barrier. Corrupt local
  files and compatibility writers are tested in Rust, not generated by these
  honest protocol transitions. A successful model is not evidence that corrupt
  stores can be admitted or repaired automatically.
- Token replacement is a drained restart using the same stable credential ID.
  It is not mailbox generation migration, permission inference from an outage,
  or a new quota identity. Old owner tokens cannot start a modeled request.
- Byte sizes and item identities are abstract. There is no arithmetic-overflow,
  hash, TLS, request-rate, global-slot or public-host availability proof. The
  production service's half-capacity allocation rule is outside this model.
- These are bounded safety results with Rust correspondence tests, not a
  refinement proof or a liveness/member-acceptance claim.

## Validation

The focused 23 September 2026 run explored 10,986 distinct states in each
positive configuration. All five mutants exited 12 and violated their named
invariant with complete ordered counterexamples. Each case took less than two
seconds under pinned TLC, one worker, a 512 MiB heap, seed 1 and fingerprint
index 0. These are observations for this checked source/configuration.
The complete repository manifest runner supplies fresh integrated evidence;
see [`../README.md`](../README.md).
Checked-in `counterexamples/` traces carry the exact model/config/tool hashes
and do not supply a current verdict.

Relevant focused Rust commands are:

```console
cargo test --locked -p vhalla-private-native --features relay-tls,client formal_relay_
cargo test --locked -p vhalla-private-native --features relay-tls,client relay::tls::tests::
```
